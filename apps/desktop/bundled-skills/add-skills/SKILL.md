# 如何沉淀技能（Skill）

## 这是什么

技能是一段**按需加载的指令**。你把运维知识、操作手册、排查 SOP 写成技能文件后，AI 在对话中可以通过 `skill` 工具随时加载这些内容，就像请了一位专门的专家加入对话。

技能**不会**一直占用上下文空间——只有被调用时才加载。这意味着你可以积累几十上百个技能，而不用担心对话变慢。

## 技能放在哪里

DSH 会从以下几个位置寻找技能（优先级从高到低，同名技能高优先级覆盖低优先级）：

| 位置 | 路径 | 适合放什么 |
|---|---|---|
| 项目级 | `项目根/.dsh/skills/` | 跟这个项目强相关的知识（部署流程、业务规则等） |
| 项目级（兼容） | `项目根/.agents/skills/` | 同上，兼容 Claude Code 的习惯 |
| 用户级 | `~/.dsh/skills/` | 你个人常用的技能，所有项目都能用 |
| 用户级（兼容） | `~/.agents/skills/` | 同上 |
| 内置（bundled） | 随应用打包 | 产品默认带的技能，比如本教程 |

**Portable 模式**下，用户级目录在应用旁的 `data/home/skills/`。

推荐：
- **团队共享的运维知识** → 放在项目仓库的 `.dsh/skills/` 里，跟代码一起版本管理
- **个人常用的工作流** → 放在 `~/.dsh/skills/` 里

## 怎么写一个技能

每个技能是一个目录，里面至少有一个 `SKILL.md` 文件：

```
my-first-skill/
└── SKILL.md
```

复杂的技能还可以带引用文件、模板、脚本等：

```
ops-deploy/
├── SKILL.md
├── references/
│   └── rollback-checklist.md
└── templates/
    └── deploy-announcement.md
```

### SKILL.md 的结构

`SKILL.md` 以 YAML frontmatter 开头，后面是 Markdown 正文：

```markdown
---
name: ops-deploy
description: 生产环境部署的标准操作流程，包含发布前检查、灰度步骤、回滚预案和验证清单
user-invocable: true
---

# 生产部署 SOP

## 发布前检查
...
```

### Frontmatter 字段说明

| 字段 | 必须 | 说明 |
|---|---|---|
| `name` | ✅ | 技能的唯一标识，用小写字母加连字符。AI 和用户都通过这个名字调用技能。 |
| `description` | ✅ | 一句话说明这个技能是做什么的。**写得越精准，AI 越知道什么时候该用它。** 要包含"什么时候用"而不仅是"里面有什么"。 |
| `user-invocable` | ❌ | 用户能不能直接调用（`/skill 名字`）。默认 `true`。 |
| `disable-model-invocation` | ❌ | 设为 `true` 时 AI 不能主动调用这个技能，只能由用户手动加载。默认 `false`（AI 可以主动调用）。 |

### 写好 description 的技巧

- ❌ 不好：`部署相关的知识`（太宽泛，AI 不知道什么时候用）
- ✅ 好：`生产环境部署的标准操作流程，包含发布前检查、灰度步骤、回滚预案和验证清单`（明确场景和内容）

description 是 AI 判断「该不该调用这个技能」的主要依据。

## 正文写什么

技能正文就是给 AI 看的详细指令。根据技能类型不同，结构也不一样。以下是几种常见类型的参考结构。

### 类型一：操作手册 / SOP

```markdown
# 生产部署 SOP

## 适用场景
什么时候该走这个流程，什么时候不该走。

## 发布前检查
- [ ] 代码已合并到主干
- [ ] CI 全绿
- [ ] 数据库迁移脚本已评审
...

## 发布步骤
1. 打标签
2. 触发流水线
3. 观察灰度指标
...

## 回滚预案
- 触发条件
- 回滚步骤
- 回滚后的验证

## 验证清单
- 功能验证
- 性能验证
- 监控验证
```

### 类型二：故障排查指南

```markdown
# 数据库连接故障排查

## 症状识别
哪些现象说明是数据库连接问题。

## 排查步骤（按可能性排序）

### 1. 检查连接池状态
命令：`...`
看什么指标：...
正常范围：...

### 2. 检查网络连通性
...

## 常见原因与解决方案

### 原因 A：连接池耗尽
现象：...
处理：...

### 原因 B：网络分区
现象：...
处理：...
```

### 类型三：规范 / 标准

```markdown
# 日志命名规范

## 原则
- 日志级别使用规则
- 禁止打印的内容

## 字段命名
- `trace_id`：...
- `user_id`：...
...

## 反例
列出常见的错误写法和修正建议。
```

## 写作原则

1. **面向 AI 写，不是面向人写。** 内容要具体、可执行、有判断标准。AI 没法猜你的意思。
2. **给出判断标准。** 不说"观察指标"，要说"观察 QPS 是否低于 X，错误率是否高于 Y%"。
3. **按重要性排序。** AI 倾向于从头读，把最关键的信息放在前面。
4. **保持简洁。** 技能是工具不是书，几百字到几千字合适。太长的内容 AI 也记不住。
5. **用结构化格式。** 列表、表格、步骤比大段文字更容易被 AI 准确理解。

## 完整示例

以下是一个最小可用的技能，直接照着改就能用：

```markdown
---
name: oncall-handbook
description: 值班期间处理告警和故障的标准流程，包含告警分级、升级路径、沟通模板和事后复盘要求
---

# 值班手册

## 告警分级

- **P0**：核心业务不可用 → 立即响应，5 分钟内升级
- **P1**：重要功能受损 → 15 分钟内响应
- **P2**：体验问题或潜在风险 → 工作时间处理

## 处理流程

1. **确认影响范围**
   - 哪个业务线、多少用户
   - 从什么时候开始的
2. **通知相关方**
   - P0/P1 拉故障群
   - @对应业务的负责人
3. **定位原因**
   - 查看监控大盘
   - 检查最近的变更
4. **止损优先**
   - 能回滚就先回滚
   - 能降级就先降级
5. **恢复验证**
   - 业务指标恢复正常
   - 错误率归零

## 沟通模板

### 故障开始
```
【故障通知】<标题>
- 级别：P0/P1/P2
- 影响：...
- 负责人：...
- 当前进展：...
```

### 故障恢复
```
【故障恢复】<标题>
- 恢复时间：...
- 根因：...
- 后续动作：...
```

## 事后复盘

P0/P1 故障必须在 2 个工作日内完成复盘文档，包含：
- 时间线
- 根因分析
- 改进项（有负责人和截止日期）
```

## 让 AI 主动用起来

写好技能后，AI 不一定每次都能精准找到它。可以这样提升命中率：

1. **description 写清楚触发场景。** 比如加上"当用户问 X 时用"、"用于处理 Y 场景"。
2. **名字用关键词。** 比如 `deploy-sop` 比 `runbook-001` 更容易被 AI 匹配。
3. **正文开头先总结用途。** AI 有时只看开头就决定技能对不对路。

如果 AI 还是不用，你可以手动调用：`/skill 技能名`。

## 技能的更新与维护

- 技能文件改了之后**自动生效**（系统会监听文件变化），不需要重启。
- 技能是纯文本文件，可以用 Git 管理，跟代码一起走 PR 流程。
- 建议定期清理过时的技能，避免太多无效技能干扰 AI 的选择。

## 从哪里开始

如果你第一次做这件事，建议按这个顺序：

1. 选一个你最常被问到的问题（比如"怎么部署"、"怎么排查数据库连接问题"）
2. 照着上面的模板写第一个技能
3. 放到项目的 `.dsh/skills/` 里
4. 在对话里试几次，根据 AI 的使用效果调整 description 和内容
5. 用得顺手了，再慢慢加更多
